# AI Reply Credits Rollout (v0.9)

Phase 30 meters the "Generate AI reply" action. This note covers what changes on deploy, why every
organisation will see AI replies fail until an operator enables it, how to enable one, and the
interim operational procedures that hold until later v0.9 phases ship.

All shell commands assume the session setup in [README.md](README.md) (root on the EC2 instance,
`ECR_IMAGE` exported). Use ids only when you record or share output: never paste review text.

## What changed

- `POST /api/v1/reviews/{id}/generate-reply/` is now metered per shop, per UTC month.
- The cost is 1, 2 or 3 credits, chosen by the length of the trimmed review comment (an empty
  comment is not chargeable and is rejected before anything is reserved).
- A successful response carries `credits_charged` and `credits_remaining` next to `draft`.
  Moderation (422) and OpenAI failure (502) responses carry the same two fields.
- `GET /api/v1/reviews/{id}/credit-cost/` is new and read-only: it returns `cost`, `remaining` and
  `is_enabled` for the review's shop. It never writes a row.
- The generate throttle is unchanged (10 per minute per user).
- Order of events per click: reserve credits, call OpenAI (no database transaction held), then
  commit on success or refund on failure.

## Rollout state: every organisation starts at 0

There is no backfill. `Organisation.monthly_credit_allocation` defaults to `0`, so after this
deploy every AI reply returns **402 with reason `not_enabled`** until an allocation is set. No
balance row or ledger row is written for those clicks.

Known interim UI behaviour:

- The composer handles 402 inline: "AI replies aren't enabled for this shop." for `not_enabled`,
  and "Not enough credits — ..." with a Buy More link when the balance is exhausted. A 409 shows
  "A reply is already being generated for this review. Please wait a moment."
- A fast tone switch can briefly return 409 while the first request for the same review is still
  settling (one reservation per review at a time). This clears on its own within seconds.

## Phase 33 behaviour changes

Phase 33 adds credit visibility for Org Admins and Staff and scopes Staff to their shops.

- **Staff shop scoping (behaviour change).** `GET /api/v1/shops/` and `GET /api/v1/shops/{id}/`
  now return only shops in the user's StaffAccessScope. This applies to web and JWT mobile
  clients alike: Staff previously saw every shop in their organisation and now see only theirs.
  Retrieving an out-of-scope shop returns 404, and a Staff user with no scope sees an empty list.
  Org Admins are unchanged.
- **New read endpoint.** `GET /api/v1/shops/{id}/credits/` (Org Admin and in-scope Staff) returns
  the shop's current-month balance (`allocated`, `bonus`, `consumed`, `remaining`, `total`,
  `is_enabled`, `period_label`, `renews_on`). It sends `Cache-Control: no-store`, is throttled at
  120/minute (`shop_credits`), writes nothing, and answers 404 `shop_not_found` for out-of-scope,
  cross-organisation and unknown shops.
- **Shops list carries credits.** Each row has `credits_allocated`, `credits_bonus`,
  `credits_remaining` and `credits_total`.
- **Activity Log.** Org Admins now see credit events (`shop.credits.*` and
  `organisation.credits.set`) with the shop name; per-review rows also show the credit count and
  review ("Credits used: 2 — {shop} · Review #{id}"). The Type filter has a "Credits" option
  (Org Admin only) and the shop filter keeps that shop's credit rows. Staff never see credit
  events or credit numbers.
- **AI reply generated events (CVIS-06).** Every successful generation writes an
  `ai_reply_generated` row on the review ("AI reply generated (Professional)"). Org Admins and
  in-scope Staff see it; it carries only the tone.
- **Superadmins are anonymous to tenants (CVIS-07).** Rows written by a Superadmin show
  "ReviewBee Admin" with no user id, and the actor dropdown has one "ReviewBee Admin" option
  (`actor=platform`).
- **Date filter.** The Activity Log date range is inclusive of the whole end day, compared in UTC.
- **Composer copy.** The AI button reads "Generate with AI (requires N credits)" and, when no
  warning applies, the line under it reads "N of M credits left this month" (the `credit-cost`
  response now includes `total`).
- **Buy More Credits** opens a mailto to `REVIEWBEE_SUPPORT_EMAIL`; no payment flow and no review
  text is included.
- **Still true:** organisations start at 0 credits. Every AI reply returns 402 `not_enabled`
  until a Superadmin sets an allocation (see below).

## Enable an organisation

Use the Superadmin UI. Superadmin, Organisations, open the row menu, Edit, set **Monthly credits
per shop** (0 to 10,000), then **Save Changes**.

- **0 to N applies immediately** when no shop of the organisation has held credits yet this month.
- **Any other change applies from the 1st of next month.** Shops keep this month's value; the
  form hint states which case applies before you save.
- To top up one shop for the current month, use the row menu, **Manage Credits**, then **Add
  bonus**. A bonus never changes the monthly allocation and is lost at month end like any other
  unused credit.
- The Django admin shows the allocation field read-only (Phase 32 D-22); do not edit it there.

Shell fallback, only when the UI is unavailable. Call the service, which records the
`organisation.credits.set` audit row and materialises current-month balances (CRED-06):

```bash
docker compose -f /opt/review-master/docker-compose.prod.yml \
  run --rm web python manage.py shell -c "
from apps.organisations.models import Organisation
from apps.organisations.services.organisations import update_organisation
org = Organisation.objects.get(pk=<ORG_ID>)
update_organisation(organisation=org, actor=None, monthly_credit_allocation=<N>)
"
```

Never use a bulk queryset `.update(...)` for this: it skips the current-month materialisation
(shops that have not used credits yet would silently take the new value this month) and the
audit row.

Behaviour to know:

- 0 to N while no shop has a current-month balance with a positive allocation applies at once:
  any zero-allocation rows left by an earlier bonus are raised to N.
- Any other change (including N to a different N, or N to 0) materialises every shop's current
  month row at the old value first, then saves the new value, so it takes effect from next month.
- Reads for a shop with no row yet use the organisation's live allocation until the first
  generate creates the row.
- Balance rows only appear once an organisation is enabled and a shop is used (or an allocation
  change or bonus materialises them).

## Operational notes

- **Timeouts.** The reply OpenAI call times out at 30 s with 1 retry, and the moderation calls
  are bounded by the same timeout. The worst case for one request is about 190 s, under the
  5-minute reservation TTL (`REVIEWBEE_CREDIT_RESERVATION_TTL_MINUTES = 5`).
- **Client disconnect.** Settlement runs server-side in the request's `finally`, so it completes
  even if the browser disconnects. If Daphne or Caddy enforce a timeout shorter than the worst
  case, the user sees an error while settlement still completes (to be confirmed against the
  deployed proxy settings, research A1).
- **Stranded reservations.** The reaper now releases a `RESERVED` row automatically once it is
  older than the 5-minute TTL (see the section below); use the manual query and refund here only
  when the reaper is disabled or failing. A container restart in the middle of a request can
  leave a `RESERVED` row behind. It holds its credits and blocks that review with 409 until
  released. Find rows older than the TTL:

  ```bash
  docker compose -f /opt/review-master/docker-compose.prod.yml \
    run --rm web python manage.py shell -c "
  from datetime import timedelta
  from django.utils import timezone
  from apps.credits.models import CreditTransaction
  rows = CreditTransaction.objects.filter(
      status='RESERVED', created_at__lt=timezone.now() - timedelta(minutes=5)
  )
  print(list(rows.values_list('pk', 'shop_id', 'review_id', 'credits_delta', 'created_at')))
  "
  ```

  Release each one (refund: restores the credits and unblocks the review):

  ```bash
  docker compose -f /opt/review-master/docker-compose.prod.yml \
    run --rm web python manage.py shell -c "
  from apps.credits.services.consumption import refund_reservation
  print(refund_reservation(transaction_id=<TX_ID>, reason='manual_ops'))
  "
  ```

  `True` means this call released it; `False` means it was already settled.
- **`shop.credits.late_commit`.** An `AuditLog` row with this action, plus a Sentry warning
  (`credits.late_commit`), means a generation finished after its reservation had already been
  released. The row's `outcome` says what happened: `rededucted` (credits were charged again,
  recorded as a new COMMITTED row with note `late_commit`), `free_draft` (the user kept the
  draft and was not charged, for example the month had rolled over or no capacity remained), or
  `already_settled` (the reservation was already committed, nothing changed). Occasional rows
  are expected around restarts; a steady stream means requests are outliving the TTL.

## Monthly lapse and reservation reaper (Phase 31)

Two Celery Beat schedules keep the credit ledger tidy. Both are seeded by data migrations and run
on the `default` queue.

| PeriodicTask name | Task | Schedule | Queue |
|---|---|---|---|
| `credits_lapse_expired_balances` | `apps.credits.tasks.lapse_expired_credit_balances_task` | Daily 00:05 UTC | `default` |
| `credits_reap_stale_reservations` | `apps.credits.tasks.reap_stale_reservations_task` | Every 10 minutes | `default` |

### What the lapse does

Every past-month balance that has not lapsed yet is closed out. When credits remain, it writes one
`LAPSED` ledger row for the remaining amount plus one `shop.credits.lapsed` audit row. The
`lapsed_at` marker is always set, even when nothing remained. `allocated`, `bonus` and `consumed`
are never changed. A balance that still holds a `RESERVED` row is skipped and lapses on a later
run: up to 24 hours later, or within 10 minutes when the reaper releases the reservation first.
The job is a no-op on most days and heals a missed night (the 1st-of-month run is the same job).

### What the reaper does

Each run refunds `RESERVED` rows older than `REVIEWBEE_CREDIT_RESERVATION_TTL_MINUTES` (5), oldest
first, through `refund_reservation` with reason `reaped_stale`. It writes one WARNING log
`credits.reaped` per refunded row and one Sentry warning `credits.reaper.reaped count=N` per run
(none when nothing was reaped). At most `REVIEWBEE_CREDIT_REAPER_BATCH_SIZE` rows are handled per
run; the rest roll to the next run. After refunding, it lapses any past-month balance it touched.
A row that was committed in the meantime is skipped, never refunded.

### Settings

| Setting / env var | Default | Meaning |
|---|---|---|
| `REVIEWBEE_CREDIT_LAPSE_CHUNK_SIZE` | 500 | Balances fetched per page by the lapse sweep |
| `REVIEWBEE_CREDIT_REAPER_BATCH_SIZE` | 500 | Max stale reservations refunded per reaper run |
| `REVIEWBEE_CREDIT_RESERVATION_TTL_MINUTES` | 5 | Reservation age before the reaper releases it (not env-overridable) |

### After deploy

Run migrations, then restart the beat service so it loads the two new `PeriodicTask` rows (a
precaution; the database scheduler normally notices on its own). In Django admin, Periodic tasks
should show `credits_lapse_expired_balances` and `credits_reap_stale_reservations`, both enabled.

### Manual runs

From the Django shell (session setup as above). Both are safe to re-run at any time:

```bash
docker compose -f /opt/review-master/docker-compose.prod.yml \
  run --rm web python manage.py shell -c "
from apps.credits.services.lapse import lapse_past_balances
from apps.credits.services.reaper import reap_stale_reservations
print(lapse_past_balances())
print(reap_stale_reservations())
"
```

Each prints its summary (counts only).

### Sentry: `credits.reaper.refund_failed`

`credits.reaper.refund_failed tx_id=<id> balance_id=<id>` means the refund could not apply: the
balance's `consumed_credits` is lower than the reservation, so the balance and the ledger disagree
for that reservation. The row stays `RESERVED` and the balance stays unlapsed. The alert repeats
every 10 minutes until fixed, because the same row is retried each run. To investigate, compare
`consumed_credits` on the balance with the sum of live CONSUMPTION rows (`RESERVED` or
`COMMITTED`) for that balance, then correct it through the incident process. Do not hand-edit
ledger rows.

### Alert handoff

The "lapse not complete by 00:30 UTC" alert is owned by the deployment owner and lives outside
this repo. A suggested check: on the 1st of the month after 00:30 UTC, the number of past-period
balances with `lapsed_at` NULL and no `RESERVED` rows should be 0:

```bash
docker compose -f /opt/review-master/docker-compose.prod.yml \
  run --rm web python manage.py shell -c "
from django.db.models import Q
from apps.credits.models import CreditTransaction, ShopCreditBalance
from apps.credits.services.periods import current_period
p = current_period()
held = CreditTransaction.objects.filter(status='RESERVED').values('shop_credit_balance_id')
print(
    ShopCreditBalance.objects.filter(
        Q(period_year__lt=p.year) | Q(period_year=p.year, period_month__lt=p.month),
        lapsed_at__isnull=True,
    ).exclude(pk__in=held).count()
)
"
```
