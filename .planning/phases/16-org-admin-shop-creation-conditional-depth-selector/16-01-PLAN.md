<objective>
Extend the backend so the shop creation endpoint accepts and persists an optional
sync_depth field, and expose the allow_custom_sync_depth org flag to the shop
management page via a Django json_script bootstrap tag.

Purpose: Give the frontend two wires it needs — a validated sync_depth that
flows from serializer through perform_create into create_shop(), and a server-side
boolean it can read at page render time without an AJAX call.

Output: Modified ShopCreateSerializer (ChoiceField), extended create_shop()
signature, extended shop_list view context, one new json_script tag in the
template, and tests covering all four behaviors.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST /api/v1/shops/ | Untrusted sync_depth string from request body |
| Django template → browser script tag | allow_custom_sync_depth boolean injected into page HTML |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-01 | Tampering | ShopCreateSerializer.sync_depth | mitigate | serializers.ChoiceField(choices=Shop.SyncDepth.choices) rejects any value not in the enum with 400; no privilege escalation possible via an invalid string |
| T-16-02 | Tampering | POST /api/v1/shops/ with sync_depth when org flag is False | accept | D-05: backend accepts any valid sync_depth silently; the org flag is a UX gate, not a security boundary; no access control difference between TWO_YEARS and ONE_YEAR |
| T-16-03 | Information Disclosure | allow_custom_sync_depth in shop_list template | accept | The flag is a per-org boolean with no PII or privilege implication; json_script renders it safely inside a type="application/json" script tag (not executable JS); XSS not possible |
</threat_model>
