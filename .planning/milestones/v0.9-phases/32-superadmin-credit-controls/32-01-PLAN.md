<objective>
Lead with the CRED-06 core end to end: Superadmin PATCH -> OrganisationUpdateSerializer -> update_organisation (atomic, organisation row locked, old value read from the locked row) -> set-based materialisation of current-month balances at the old value -> field save -> one organisation.credits.set AuditLog row -> the organisation list exposing both the saved value and this month's value. Then prove every CRED-06 timing edge (0 -> N immediate, D-18 deferral, zero-row raise, N -> 0, next month, idempotency, rollback, equivalence with ensure_balance, query ceilings) and finish CRED-01 (create field, validation, Org Admin/Staff 403 on the PATCH field, read-only Django admin).

Purpose: CRED-06 is the riskiest part of the phase (research Summary: "The hard part is CRED-06, not the bonus"). The virtual-balance fallback reads the organisation's live allocation, so saving N -> M without materialising first would silently move every unmaterialised shop to M this month. Shipping the whole write path on the first commit proves the lock, ordering and audit design before the bonus (Plan 32-03) builds on the same lock order.

Output: two set-based helpers in apps/credits/services/allocation.py, two read helpers in apps/credits/selectors/balances.py, the atomic update_organisation with actor and audit, create_organisation accepting the field, serializer fields, the list annotation, the admin read-only field, and the tests.

Decisions implemented here: D-02, D-03, D-04, D-15 (data source), D-18, D-20, D-21 (server field), D-22, plus the accepted planner guidance in CONTEXT ("update_organisation gains actor, @transaction.atomic, and select_for_update on the org row ... create_organisation accepts the field"). Claude's discretion recorded: AuditLog naming for organisation.credits.set uses entity_type "organisation" and entity_id str(org.pk) (research A5); create audits only when the value is > 0 (a default of 0 is not a change, research Pitfall 9); D-15's "pending" is derived as current_month_credit_allocation != monthly_credit_allocation, a read that never writes.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (Superadmin session) -> PATCH/POST /api/v1/organisations/ | Untrusted JSON crosses into the org-edit service that writes balances, ledger and audit rows for every shop of a tenant |
| Org Admin / Staff session -> same endpoints | Lower-privilege roles must not reach the credit allocation |
| Concurrent writers (another org edit, a bonus, a first-use ensure_balance from the reply path) -> the same organisation's balance rows | Ordering and locking decide which allocation a shop holds this month |
| Django admin -> Organisation row | A second write path that would skip CRED-06 and the audit row |
